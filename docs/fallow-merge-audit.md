# The fallow merge audit

`git merge` never went through the fallow gate. Two git post-hooks now audit the
post-merge tree and **warn, never block**.

## Install

```bash
scripts/install-git-hooks.sh              # installs the ledger AND the merge audit
scripts/install-git-hooks.sh --status
scripts/install-git-hooks.sh --uninstall
```

Same installer as the [commit ledger](commit-ledger.md); same common-dir rule, so
one install covers the main checkout and every linked worktree.

## What was broken

`.claude/hooks/fallow-gate.sh` is a Claude Code **PreToolUse** hook. It decides
whether to audit with one regex:

```
git[[:space:]]+(commit|push)
```

`git merge` writes a commit object without ever invoking `git commit`, and so
does `git merge --continue`. Neither string matches, so neither fired the audit.
During `epic-the-wall-ii`, **25 merges onto `main` landed with no audit at all**.

That is how the `SheafPane` CRAP regression reached `main`: `wall-copy-affordance`
and `wall-sheaf-only-projects-with-something` were each under the bar in their own
worktree, the merged component was over it, and the merge that summed them was
never looked at. It surfaced hours later, by accident, on an unrelated commit.

At gen 22 the mirror image happened: a `git commit` of a conflict resolution was
blocked and a `git merge --continue` of the **identical tree** went straight
through. Same content, same verdict, opposite outcome, decided only by which verb
wrote the commit.

## Why it warns instead of blocking

Adding `merge` to that regex is the obvious fix and it is the wrong one.

Two independently-approved, green branches can sum to a `fail` that **neither one
introduced and neither one can fix**. At gen 23 that was one coin-flip wide: two
approved branches sat ready at once against a `main` that already carried a `fail`
verdict, and merge order was free choice. Had the unrelated broker-only branch
gone first, a blocking merge gate would have refused it on a web finding it never
touched -- with no escape but a suppression (forbidden) or pushing `main` to
re-attribute the finding as `inherited` (banking real debt as accepted).

So the ruling is **option 2: audit merges and warn, never block.** The lander sees
the finding at the moment they caused it, with both parents in hand, which is the
only moment a summed regression is diagnosable. Every path exits 0.

## Why it is a POST hook

`fallow audit` measures the tree in front of it. On a `git merge`, a PreToolUse
hook measures the **pre-merge** tree -- precisely the tree that cannot contain the
sum. A warn implemented inside `fallow-gate.sh` would faithfully report the
verdict of the state you are leaving and would still have been blind to
`SheafPane`.

Base selection is what makes the sum visible: `--changed-since HEAD^1` on the
post-merge working tree. A finding the first parent already had comes back
`inherited`; one that only exists once both sides are summed comes back
`introduced: true`.

## Why it takes TWO hooks

Verified empirically; asserted in `scripts/install-git-hooks.test.ts`:

| what you ran | post-merge | post-commit |
|---|---|---|
| clean `git merge --no-ff` | fires | -- |
| fast-forward `git merge` / `git pull` | fires | -- |
| conflict + `git merge --continue` | -- | fires |
| conflict + `git commit` | -- | fires |
| an ordinary commit | -- | -- (skipped) |

Wiring only `post-merge` would miss exactly the conflict-resolution path, which
is the path a fleet integrator hits most. The post-commit branch audits **only**
when `HEAD` has two or more parents -- ordinary commits belong to the PreToolUse
gate, which blocks, and must not be audited twice.

A fast-forward writes no merge commit, so that case audits against `ORIG_HEAD`.

## Output

Verdict `pass` prints one line. Anything else prints the finding, what this merge
introduced versus what it inherited, and where the full JSON went:

```
fallow-merge-warn: verdict 'fail' on merge commit 669028cd
  base    : cf7f39f1 (first parent -- what this merge was added to)
  changed : 1 files
  new     : 1 complexity, 0 dead-code, 0 duplication
  carried : 0 complexity, 1 dead-code, 0 duplication
  complexity  src/shared/proof-sum.ts:1  summed  cyclomatic=11 cognitive=24 crap=n/a -- exceeded cognitive
  NOTHING IS BLOCKED -- the merge already wrote.
  full report: .git/fallow-merge-warn-last.json
```

Kill switch: `RCLAUDE_FALLOW_MERGE_WARN=0`.

## The regeneration hazard

`.claude/hooks/fallow-gate.sh` carries `# Generated by fallow setup-hooks`. A
future `fallow setup-hooks` run overwrites it and silently drops anything added
there.

**Nothing that matters lives in that file.** The merge audit is entirely outside
what the generator owns: tracked sources under `scripts/git-hooks/`, installed
into `.git/hooks` by `scripts/install-git-hooks.sh`. A regeneration cannot drop
it, because it was never there.

What a regeneration *does* drop is one comment. The generated header claims it
"Blocks Claude Code git commit and git push" -- true, but for years it read as
coverage of merges it never had. The corrected wording is recorded here so it can
be re-applied, and `scripts/install-git-hooks.sh --status` reports when the live
file has lost it:

```
# Blocks Claude Code `git commit` and `git push` when fallow audit returns
# verdict fail. It does NOT see `git merge` or `git merge --continue`: neither
# invokes `git commit`, so neither matches the regex below, and a PreToolUse hook
# would measure the pre-merge tree anyway. Merges are audited after the fact by
# .git/hooks/post-merge + post-commit (warn-only). See docs/fallow-merge-audit.md.
```

`.claude/` is globally gitignored on this machine, so that file cannot be tracked
and this doc is the durable copy.
